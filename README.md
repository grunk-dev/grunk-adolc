# grunk-adolc

A [grunk](https://github.com/grunk-dev/grunk) plugin exposing
[ADOL-C](https://github.com/coin-or/ADOL-C)'s tapeless `adouble` algorithmic
differentiation (AD) type as a real, native `adtl.adouble` Lua usertype - so a
value can flow through a grunk recipe (dependency tracking, lazy evaluation, YAML
serialization) and still carry its AD derivative, *and* so that value's own C++
type is directly shared with any other native grunk plugin that also names
`adtl::adouble` (`grunk-occt`'s own AD-enabled build, for one - see `DESIGN.md`'s
"Native adtl::adouble binding, generated, not hand-written"). See `DESIGN.md` for
how this repo relates to `grunk-occt` (a sibling repo, OCCT bindings for grunk) and
the deferred, future `grunk-geoml`.

This plugin links ADOL-C's own public headers/library directly - no OCCT/CAD
dependency, and (unlike an earlier version of this repo, preserved for reference on
the `swig-adtl-plugin` branch) no SWIG/DLR-internal dependency either; see
`DESIGN.md` for why that changed. `src/adtl_plugin.cpp` is a thin entry point;
`generated/adouble.cpp` (ADOL-C's entire practically-relevant API, generated by
`codegen/generate.py` from ADOL-C's own public header - see `codegen/config.yml`)
is where almost everything actually is.

## Prerequisites

- CMake >= 3.15
- C++17 compiler
- Autotools (`autoreconf`/`automake`/`libtool`) - needed to build ADOL-C itself below;
  not needed for anything else in this repo
- [pixi](https://pixi.sh/)

### Build and install ADOL-C 2.7.2

```bash
pixi install
pixi run install_adolc
```

Downloads, builds, and installs ADOL-C 2.7.2 into `.deps/adolc` (deliberately
outside the CMake build directory - see `scripts/install_adolc.sh`'s own comment
for why: a routine `rm -rf build` must never force rebuilding ADOL-C from
scratch too) via `scripts/install_adolc.sh` - idempotent, safe to re-run. Needs
`autoreconf`/`automake`/`libtool` on `PATH`.

<details>
<summary>What this does, if you'd rather run it by hand (or it fails partway)</summary>

```bash
mkdir -p build/_deps && cd build/_deps
git clone https://github.com/coin-or/ADOL-C.git
cd ADOL-C
git checkout releases/2.7.2

mkdir -p ../../.deps/adolc
export ADOLC_PREFIX="$(cd ../../.deps/adolc && pwd)"

autoreconf -fi
./configure --prefix="$ADOLC_PREFIX" --enable-atrig-erf --with-boost=no
make -j
make install

cd ../../..   # back to this repo's own root
```

**Where ADOL-C actually installs its library** (`lib` vs. `lib64`) depends on your
distro's own autotools defaults - `CMakeLists.txt`'s own `pkg_check_modules` call
finds it either way (via `adolc.pc`), but if you ever need to know for the runtime
note below: `ls "$ADOLC_PREFIX"/lib*`.

</details>

**Runtime note:** `adtl_plugin.so` links directly against ADOL-C's own shared
library (`libadolc.so`, in `.deps/adolc/lib` or `lib64`) at *runtime*, not just at
link time - skipping this fails the plugin's `dlopen` outright with a "cannot open
shared object file: libadolc.so" error. `pixi.toml` already sets
`LD_LIBRARY_PATH`/`PKG_CONFIG_PATH` for every `pixi run` task
(`$PIXI_PROJECT_ROOT`-based, see its own comment there) covering this exact
install path - nothing further to do for any `pixi run` task below. Installed
ADOL-C somewhere else, or running `run_example.py`/`runUnitTests` directly rather
than through `pixi run`? Export both yourself first:

```bash
export LD_LIBRARY_PATH="$ADOLC_PREFIX/lib64:$LD_LIBRARY_PATH"                       # or lib
export PKG_CONFIG_PATH="$ADOLC_PREFIX/lib64/pkgconfig:$PKG_CONFIG_PATH"             # or lib
```

## Building and running

```bash
pixi run all
```

Or step by step:

```bash
pixi run install_adolc   # build/install ADOL-C, if not already done
pixi run configure        # configure the CMake build
pixi run build             # build adtl_plugin and the test harness
pixi run test                # run the gtest suite (tests/test_load.cpp, tests/test_recipe.cpp)
pixi run run_examples         # run examples/run_example.py against the built plugin
pixi run install               # install adtl_plugin into build/install (see "Packaging / installing" below)
pixi run generate_code         # regenerate generated/adouble.cpp from ADOL-C's own header
                                 # (requires -D GRUNK_ADOLC_GENERATE_CODE=ON at configure time)
```

## Packaging / installing

`adtl_plugin` is a runtime-loaded grunk plugin - a consuming application never links against it,
it dlopens it by path via `grunk::plugin::load_native` (matches grunk-occt's own `occt_plugin` -
see its README's identical section). So there's no CMake package config to `find_package()` here,
just the built shared library itself:

```
pixi run install   # -> build/install/lib/libadtl_plugin.so
```

Point `grunk::plugin::load_native` (or its Python equivalent) at the installed path instead of a
path under `build/` directly once you're consuming this outside the build tree - `examples/`/
`tests/` in this repo itself still reference the build tree directly, since they're meant to run
right after `build`, not `install`. `CMAKE_INSTALL_PREFIX` (set by the `configure` task,
`build/install`) can be overridden - either edit `pixi.toml`'s own `configure` task, or run
`cmake --install build --prefix <path>` yourself.

When consumed via grunk-occt's own `GRUNK_OCCT_ENABLE_AD` build (FetchContent, pinned to a
specific commit), grunk-occt's own `pixi run -e ad install` picks this up too - its FetchContent
pin was bumped to include this change once it was committed and pushed here (see grunk-occt's own
`DESIGN.md`, "Step 8: packaging").

## Examples

`examples/test_adolc.grr.yml` is a small, self-contained recipe (`uses: adtl:
2.7.2`, a recipe-local `modules:` block for its own `me.seed` helper - no external
plugin/module dependency beyond `adtl` itself) computing `w = adtl.sin((x * y) *
6)` with `x` seeded for forward-mode AD from a parameter. `examples/run_example.py`
loads the plugin, overrides the seed parameter, and checks both the resulting
value and derivative against the closed form (`sin(102*x_val)`,
`102*cos(102*x_val)`) - see its own doc comment.
